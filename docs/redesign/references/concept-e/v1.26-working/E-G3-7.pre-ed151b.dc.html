G3-7 · iPhone keyboard and the teal "Add" key

Decision board · awaiting your choice6 Nov · no active board changed

You asked for the keyboard's key to read "Add" in teal instead of iOS's blue "done" (ED-030 rejected blue "done"; ED-031 accepted teal Add). The boards draw that as a custom key on the iOS keyboard. A real iPhone app cannot restyle or relabel the system keyboard's keys, and iOS has no "Add" return key. This board shows the current drawing, what iOS really does, and three ways to keep a teal Add within reach while using the real keyboard. You also wrote "the keyboard" afterwards (ED-032), never answered: options A and C settle it by drawing the stock keyboard.

1 · The issue

Why it matters across Dottoday

  • Quick add is the core flow (R-06): a task in two taps plus typing. Whatever confirms the task must be obvious and reachable with the keyboard up.
  • Native-first (G3-6, ED-128): the keyboard is iOS's own; drawing a key iOS cannot show would mislead implementation and break the real keyboard's dictation, languages, autocorrect and accessibility.
  • One rule per platform: iPhone, iPad, Android, Mac and web each confirm differently (Return, Enter, Gboard's action key). The drawing should match what each platform can do.
  • No shame, no blue: ED-030 keeps iOS blue "done" off the Add keyboard; the return key must stay neutral.

What iOS and Android allow (checked against the platform APIs)

  • iOS return key: the app picks one of iOS's types (return, go, join, next, route, search, send, done, continue …). There is no "Add". The accent types (done, go, send …) show in the system blue; only the plain "return" type stays neutral. Colour and label cannot be changed.
  • iOS accessory bar: a bar riding on top of the keyboard is standard (Notes, Mail). In Flutter it is an app-drawn bar that follows the keyboard inset; a native UIKit inputAccessoryView does not attach to Flutter text fields.
  • Custom keyboard: replacing the whole keyboard is possible only as a custom input view, losing dictation, autocorrect, languages, emoji and VoiceOver keyboard behaviour. Not suitable.
  • Android: the app sets the action (done, go …); Gboard draws the key in its own theme colour (often the wallpaper's), not the app's teal. Flutter cannot set a custom action label.

Accessibility (option A)

  • VoiceOver: the bar's Add is a button with the task in its label ("Add Gym"); the return key is announced by iOS ("return").
  • Touch target: 36 pt visual, 44 pt hit area; bar 44 pt tall.
  • Larger text: the bar grows with Dynamic Type (hint wraps or hides before the button shrinks).
  • Reduced motion: the bar moves only with the system keyboard; no extra animation.
  • Hardware keyboards and Full Keyboard Access: Return adds; the bar hides when no on-screen keyboard is shown.
  • Paste a list: the bar's label follows the in-field button ("Add 4 tasks"); nothing is written before the proposal is accepted.
