# 02 — Product Requirements (v1, core planner)

Format: feature → user stories → acceptance criteria (AC). `R-xx` links to `01-research-complaints.md`.
Everything here is **free tier** unless marked *Phase 2*.

Each v1 feature bullet carries a stable ID (`[F1.4]`). IDs are never renumbered or reused: a new
bullet takes the next free number in its section. `docs/parity-checklist.md` has one row per ID × iPhone,
Android, macOS and web (R-13), generated by `app/tool/parity_checklist.dart`; `parity_checklist_test`
fails when an ID has no row. "Clarified in …" bullets refine the one before and carry no ID.

## F1. Timeline (day view) — the home screen

**Stories**
- [F1.1] As a user I see today as a vertical timeline from my day start to day end, with a "now" line, so I know what's next.
- [F1.2] As a user I drag a block to a new time, or drag its top/bottom edge to change duration. (R-05)
- [F1.3] As a user I move one block and choose whether everything after it shifts too. (R-04)
- [F1.4] As a user I tap "Running late" and push all remaining unpinned blocks by +5/+15/+30 min. (R-04)
- [F1.5] As a user I pin a block so nothing ever moves it. (R-17)
- [F1.6] As a user I long-press to multi-select blocks and move/delete/duplicate them together. (R-05)
- [F1.7] As a user I see free gaps and can tap a gap to add a task there. (R-17)
- [F1.8] As a user I swipe left/right (or ←/→ keys) to move between days; a header date picker jumps anywhere.
- [F1.9] As a user I can check a block done from the timeline; past undone blocks are visually "overdue" but never nag.

**AC**
- [F1.10] Blocks render start–end time, title, icon, colour, subtask progress (3/5), and a calendar badge for imported events. (R-16)
- [F1.11] Drag: long-press 250 ms to pick up (haptic), snap to configured increment (default 5 min), live ghost preview, auto-scroll near edges. Vertical scroll never starts a drag. (R-05)
- [F1.12] Shift-followers: default from settings (`shiftFollowers: ask | always | never`), with an in-gesture toggle chip. Pinned blocks and imported calendar events are never shifted unless the user chooses "include calendar events". (R-04, R-17)
- [F1.13] Overlaps allowed; overlapping blocks render side-by-side (max 3 columns, then "+n").
  Clarified in M8.4b (replaces the columns on the thread): Concept A's thread is one axis
  (`10-ui-concept-a.md` §1, ADR-0007), so overlapping tasks render one under the other in start order,
  each a full row (never covered, each its own tap target); the live task's overrun into the next is
  what "Shift the rest" offers to clear (R-04), and the `ThreadPicker` warns before an overlap is made.
  The Mac/web Week board stacks overlaps in its day columns. Rejected: side-by-side columns (two
  parallel threads break the single axis and halve the row width on a phone).
- [F1.14] Timeline builds lazily; 200 blocks in a day scroll at ≥ 55 fps on a Pixel 6a / iPhone 12 class device. (R-15)
- [F1.15] Day boundaries: per-weekday start/end; blocks outside boundaries still render in a collapsed "outside hours" zone. (R-17)
  Clarified in M8.4b: built on the thread as `ThreadOutside` — tasks that end by Wake Up fold into one
  row above the sun cap ("2 tasks before Wake Up"), tasks that start at Bedtime or later into one below
  the moon cap ("1 task after Bedtime"); a tap unfolds them into ordinary rows (open, done, drag,
  select). A task across a cap stays inline; a zone holding the live task starts unfolded. The Week
  board still shows every task.
- [F1.16] Full 24 h renders — golden test for the bottom of the day. (R-14)
  Clarified in M8.4b: the latest Bedtime is 23:55 (the Day shape slider's last step; `24:00` is not a
  valid window end, `checkTimeWindow`), so "the bottom of the day" is Bedtime 23:55 with a 23:30 task:
  `today_bottom_golden_test` scrolls the thread to its end at compact and expanded widths.
- [F1.17] Keyboard (desktop/web): ↑↓ select, Enter open, Space complete, ⌘/Ctrl+↑↓ move 5 min, Shift for 15, Delete → trash with undo.
  Clarified in M8.4b: the ↑↓ pick *is* the multi-select (`TaskSelection`, R-05) — one task at a time,
  in start order on the shown day, so the selection bar shows and ⌘/Ctrl+↑↓ and Delete act on every
  picked task (one undoable batch; pinned tasks stay, R-17). Delete/⌫ trashes without a confirm (Undo
  is the safety, F1.18); Esc drops the pick; ↩ and Space act only with exactly one pick, otherwise the
  focused control keeps them. A picked row scrolls into view and unfolds its outside-hours zone.
- [F1.18] Undo snackbar (30 s) for every move/delete/complete. (R-11)

## F2. Quick Add & Task Editor

**Stories**
- [F2.1] As a user I type "Gym 7am 45m" and get a block at 07:00 for 45 min. (R-06)
- [F2.2] As a user I paste five lines and get five inbox tasks. (R-07)
- [F2.3] As a user I open the full editor only when I want details (notes, subtasks, colour, icon, alerts, recurrence).

**AC**
- [F2.4] Quick Add field is reachable from any screen (FAB on mobile, ⌘/Ctrl+N on desktop/web).
- [F2.5] Parser handles: times (7am, 19:00, noon), relative days (today, tomorrow, Friday, next Mon), durations (45m, 1.5h, 2 hours), "every day/week/Mon,Wed" → recurrence prefill, "@inbox" → no time. Unparsed text stays as title. Parsed tokens are highlighted and removable with one tap. Unit-tested in en, de, fr, es with 24-h/12-h locales. (R-06, R-20)
  Clarified in M1.5 (`domain/quick_add/`): a time with no date means *today*, even if already past (the
  date never jumps on its own, R-20); "Friday" is the next Friday on or after today, "next Friday" strictly
  after; `HH:MM` and `7pm` parse in every language and the 12/24-h setting only changes chip display;
  French `15h`/`15h30` is a clock time (durations use `min`/`heures`); one token per kind, later ones stay
  title; two-letter German weekday abbreviations and es `mar` are not recognised (everyday words);
  input over 10 000 chars is rejected (06 §7).
- [F2.6] Time entry is always typeable; wheel/picker optional. One shared `TimeInput` component. (R-20)
- [F2.7] Duration chips 15/30/45/60/90 + custom; range 5 min–24 h. (R-16)
- [F2.8] "Add another" keeps the sheet open; multi-line paste → one task per non-empty line. (R-07)
- [F2.9] Editor fields: title (required, ≤ 200 chars), notes (markdown-lite, links tappable, ≤ 10 000 chars), start, duration, colour, icon, subtasks (≤ 50), alerts (≤ 5), recurrence, pinned, travel-time buffer (0–180 min), energy level (optional, low/med/high). (R-02, R-17)
  Clarified in M8.4c: energy is three chips (Low · Medium · High) under ENERGY in the editor; tapping
  the picked chip clears it (no fourth "None" chip). An edit of a repeating task's energy asks the
  series scope like any other field. Markdown-lite is `**bold**`/`__bold__`, `*italic*`/`_italic_`,
  `- `/`* `/`• ` bullets, `1. ` numbered items, `[label](https://…)` and bare web links; headings,
  code and anything else stay as typed. The editor keeps the source (a helper line names the syntax);
  the task sheet renders it under NOTES. Links are drawn as links inline, and the LINKS rows below
  stay what a tap opens (44 pt rows a screen reader lists, R-12); a line that is only a listed link is
  not repeated. In-repo renderer, no package (rejected: a markdown package — a new dependency for
  four constructs; a WYSIWYG field — a new concept on four platforms).
- [F2.10] Saving is optimistic; the sheet closes immediately.
- [F2.11] Subtasks gain an optional duration each and an order; a task's duration may be the sum of its steps.
  Occurrences record actual start and actual end timestamps when the user starts/completes them
  (`11-standout-roadmap.md` B1, B2).

## F3. Inbox

- [F3.1] Unscheduled tasks live in the inbox; drag from inbox onto the timeline, or tap → "Schedule" with smart suggestions (next free gap today, tomorrow morning, pick time).
  Clarified in M8.4c: dragging an Inbox task onto the thread is the expanded (≥ 840 px) path, where
  the Inbox sidebar sits beside Today. On compact and medium widths the Schedule sheet is the path:
  `+` or a swipe left opens it, and "Pick time" places the task by dragging it on that day's
  thread (`ThreadPicker`). Rejected: a cross-tab drag on phones — Inbox and Today are separate tabs,
  so the drag would have to switch tabs mid-gesture, and a row's long-press (menu) and handle
  (reorder, F3.2) already own the gestures.
- [F3.2] Inbox supports reorder, swipe-to-schedule, swipe-to-trash, bulk select.
- [F3.3] An inbox badge shows count; an optional "plan your inbox" nudge appears once per day at day start (dismissible, off by default).
  Clarified in M8.4c: the badge is the open Inbox count on the Inbox tab / rail item on every width,
  in the accent (never red), "99+" past 99, and the tab's screen-reader name carries it ("Inbox, 3
  tasks"). The nudge is a card on Today above the thread (Settings › Planning › "Plan-your-inbox
  nudge", off by default): it shows from Wake Up to Bedtime while the Inbox holds open tasks, unless a
  more pressing prompt (Day review, Running late) is up; Plan opens the Inbox, and Plan or Not now
  puts it away until the next day on this device. Rejected: a local notification at Wake Up — it
  would spend the iOS 64-pending budget (07) on a suggestion, and the reminder settings are M8.4d's.

## F4. Recurrence

- [F4.1] RRULE-based: daily, weekdays, weekly on chosen days, every N days/weeks/months, monthly by day-of-month or nth weekday, yearly; end never / after N / on date. (R-01)
- [F4.2] Edit scope dialog: this occurrence / this and following / all.
- [F4.3] Exceptions: skip, reschedule, or modify a single occurrence without breaking the series.
- [F4.4] Subtasks are defined on the series template and instantiated per occurrence; completion is per occurrence. (R-09)
- [F4.5] DST and month-end rules follow RFC 5545; tests cover 31st-of-month, Feb 29, DST spring/fall in Europe/Berlin and America/New_York.
- [F4.6] Occurrences are materialised 90 days ahead on device (rolling), so the timeline and widgets work offline.

## F5. Calendar import & write-back

- [F5.1] Connect Apple Calendar (iOS/macOS via EventKit), Google Calendar, Microsoft 365 (OAuth via backend), device calendars on Android. (R-02)
- [F5.2] Per-calendar toggle, colour inheritance, all-day events shown in a header strip (editable). (R-02)
  Clarified in M7.1: connecting turns every calendar on (switch off the ones you don't want; a
  calendar added to the device later comes in too). An event takes the task colour nearest to its
  calendar's colour. A multi-day all-day event shows in the strip on each of its days; tapping a strip
  item opens it to edit.
- [F5.3] Imported events are first-class blocks: draggable, resizable, can have subtasks/notes stored locally (never written to the external calendar unless the user enables write-back for that calendar). (R-02, R-09)
  Clarified in M7.2: events from yesterday to 90 days ahead come in on start, on resume, every
  6 hours and right after a calendar is switched or connected. An event's description and link
  become its notes. Subtasks, notes, moves and renames made in Dottoday stay on this device (each
  device imports its own calendars) and stay put until the calendar changes that same thing; notes
  edited here are never overwritten. An event deleted from its calendar disappears here too —
  into Trash if it had subtasks, notes or a tick. Deleting an imported event in Dottoday hides it
  (it doesn't come back). Imported events don't remind in Dottoday unless you add alerts (the
  calendar app reminds already).
- [F5.4] Write-back (optional per calendar): move/resize/rename syncs to the source calendar; failures surface as a non-blocking banner with retry.
  Clarified in M7.3: Settings › Calendars › Send changes back, one switch per writable calendar,
  off until chosen; turning it on also sends moves made before. Only timed, non-repeating events
  write back (repeating instances and all-day items change here only, and the editor says so).
  Notes and subtasks never go back. A change made in the calendar meanwhile is combined with the
  one made here field by field; the same field changed in both places asks once (banner: Keep
  mine / Use calendar's). An event gone from the calendar keeps the edit here until the next
  import removes it.
- [F5.5] Travel time: if the event has a location and the user enables it, a buffer block is suggested before it. (R-17)
  Clarified in M7.5: Settings › Calendars › Travel time › "Suggest travel time" (off until chosen)
  and one length for every event (5 min–2 h, default 15). No route or maps service is asked: that
  would send the place off the device, so the suggestion is a rule on the device (rejected: a
  routing API — a cloud endpoint and a new dependency; learning a length per place — more concepts,
  follow-up if asked). An imported, timed event with a place that hasn't started and has no travel
  time shows a card in its sheet: "At Main St 4. Keep 15 min before it for getting there?" · Add 15
  min before / Not now (put away for this session). Nothing is written until Add (proposal rule; a
  one-change confirm until `ProposalSheet`, M10.2); Add is undoable and sets the event's travel
  buffer, which the thread shows as "· 15 min travel" on the row and takes out of the free gap
  before it; the sheet lists it as Travel time, and the editor's Travel time row (every scheduled
  task, None–2 h) changes or removes it. A move or a re-import keeps it. Rejected: a separate
  "Travel" task before the event (a second block to keep in step with the event when it moves).
- [F5.6] Links in event descriptions open in the browser. (R-02)
  Clarified in M7.2: the task sheet and editor list the web links (http/https, up to 5) found in
  the notes under LINKS; a tap opens the browser. Links typed into a task's notes work the same.
  Clarified in M7.4: Google and Microsoft calendars are connected in Settings › Calendars after
  signing in, on every platform including the web. Connected once, they show on every device the
  person signs in on, each calendar with its own switch on each device. Subtasks and notes on their
  events stay on the device where they were added, as for device calendars. Moves, resizes and renames
  go back when Send changes back is on for that calendar, also for one instance of a repeating event,
  and never for a meeting someone else organises. Disconnecting asks first. The events then leave
  the timeline (into Trash when they carry subtasks or notes). An account Dottoday can no longer reach
  shows Reconnect, and its events stay as they were.

## F6. Notifications & alerts

- [F6.1] Per task up to 5 alerts: at start, N minutes before (1–1440), at end, when overdue by N minutes. (R-03, R-10)
- [F6.2] Default alert set configurable in settings. Quiet hours. Per-weekday day start summary ("Your day: 6 blocks, first at 08:00") optional.
- [F6.3] Scheduling is idempotent: notification IDs derive from `occurrenceId + alertIndex`; re-scheduling after edits cancels stale IDs first. Property test: no occurrence ever has >1 pending notification per alert. (R-10)
- Clarified in M1.6 (`domain/notifications/`): alerts inside quiet hours are still delivered, but silently
  (no sound/banner, not time-sensitive), so nothing is lost; done/skipped/deleted/inbox tasks never alert;
  a snooze replaces every alert before the snooze time with one reminder (slot 5, after the 5 alert
  slots); the planner keeps the earliest 64 on iOS and plans 7 days ahead. Payloads carry the occurrence
  ID only (06 §1).
- [F6.4] Actions on the notification: Done, Snooze 10 min (shifts followers per setting), Open. (R-04)
- Clarified in M5.1: the actions bring Dottoday forward and are handled in the app (one database
  connection, no background isolate); Done ticks that occurrence only (R-09). Snooze re-reminds in 10
  minutes and moves nothing: a notification can't ask "shift the rest?", so shifting later tasks is
  offered in the app (Running late nudge/sheet) under the shift-followers setting. Tapping the body = Open.
- [F6.5] Notification text is the task title over when ("Starts in 10 minutes", "Starting now", "Ending now",
  "Ended 15 minutes ago. Done?", "Snoozed reminder"); Bedtime reads "Tomorrow starts with … at …".
  A renamed task's pending alerts are re-posted (the payload keeps a short hash of the shown text).
- [F6.6] Custom sound from a bundled set; respects system Focus/DND. (R-10)
- [F6.7] Web: Web Push via service worker when granted; fallback to in-app banner.
- [F6.8] Delivery guarantees (`11-standout-roadmap.md` A0, milestone M6.5): dot-start notifications use the
  time-sensitive interruption level on iOS and a dedicated alarm channel with exact alarms on Android;
  the first dot of the day and routine-start dots are alarm-loud by default; onboarding includes a test
  alarm; Settings › Reminders has a notification-health panel reading the real OS state (permission,
  exact alarms, battery exemption, Focus/DND, device clock).
  Clarified in M6.5.3 (`domain/notifications/alarm_policy.dart`): "first dot of the day" is the earliest
  scheduled task starting on that local day, whatever its state — if it is already done or skipped, no
  later dot becomes that day's alarm; only the at-start alert rings loud (not "before"/end/snooze);
  days follow the user's current zone, so travel re-plans them.

## F7. Sync, accounts, backup

- [F7.1] The app is fully usable without an account (local only). Creating an account enables sync. (R-08)
- [F7.2] Auth: email magic link, Sign in with Apple, Google. No passwords stored by us.
- [F7.3] Sync engine: local DB is the source of truth; change log pushed; Realtime subscription pulls; per-field last-writer-wins with vector of `updatedAt`; tombstones for deletes; conflicts logged and surfaced only if both sides changed the same field within 60 s (then "keep mine / keep theirs"). (R-08)
- [F7.4] Sync status pill: synced / syncing / offline / error (tap for details). (R-08)
- [F7.5] Automatic daily local backup (last 7 kept) + manual export JSON/CSV/ICS from any platform. Import from JSON. (R-11)
- [F7.6] Trash with 30-day restore; permanent delete requires confirmation. (R-11)
- [F7.7] Account deletion: one tap in settings, deletes server data within 24 h, confirmed by email (GDPR).

## F8. Views & navigation

- [F8.1] Today (timeline), Inbox, Week overview (compact, read + drag), Month (dots per day, tap to open day) — all free. (R-03, R-14)
- [F8.2] Search across titles/notes/subtasks including completed history. (R-11)
- [F8.3] Settings: day boundaries, snapping, shift-followers default, alerts default, theme (system/light/dark), accent colour, 12/24 h, first day of week, language, calendars, account, export, trash, feedback, changelog, about. (R-19)
  Clarified in M8.4c: the accent colour is one of Concept A's four (`10-ui-concept-a.md` §2) on every
  platform; there is no Android Material You (wallpaper) accent. The design contract is the more
  specific doc (ADR-0007), its four accents are paired light/dark values checked for contrast, and
  colours are not among the idioms platforms may vary (§4); an Android-only option would also break
  R-13 parity. Rejected: `dynamic_color` (a new dependency the design-system rules exclude) and a
  platform channel snapping the system accent to the nearest of the four (a fifth, Android-only
  concept with no iOS/web equivalent).

## F9. Home-screen widgets & watch (mobile/desktop)

- [F9.1] iOS/Android widgets: "Next up" (small), "Today timeline" (medium/large), "Inbox count". macOS: menu-bar "next up". Data comes from the local DB via an app-group/shared file; refresh on every write. (R-08)
- [F9.2] iOS Live Activity / Dynamic Island and an Android ongoing notification for the live dot; interactive
  widget actions; Control Center / Action button controls. All surfaces read the day snapshot and call
  the five App Intents only; none talk to Supabase (`11-standout-roadmap.md` A1, B5, B6).
- [F9.3] Apple Watch complication and glance: Phase 2 (not blocking v1), but data layer designed for it.
  Watch rule (ADR-0010): the watch never authenticates — no account, network or token on the wrist; the
  phone pushes the day snapshot; check-offs and +15 queue on the watch; native app (Swift / Compose).

## F10. Onboarding

- [F10.1] At most 3 input screens: pick day start/end (O2), pick first tasks (O3, skippable; suggestion chips or Quick Add), account (O5, optional). Optional calendar connect is a row on the Reminders screen (O4). Welcome (O1), Reminders (O4) and Done (O6) ask for nothing beyond the permission prompt. O4 Reminders gains "Send me a test alarm" (`11-standout-roadmap.md` A0). Skippable. Finishes in under 90 s. Screens: `10-ui-concept-a.md` §5.1.

## F11. Feedback & changelog

- [F11.1] Settings → Send feedback (opens mail composer with app version, platform, redacted diagnostics opt-in). In-app "What's new" after updates. (R-19)
- Clarified in M8.2: the draft is a `mailto:` link the person sends from their own mail app — Dottoday sends nothing. Diagnostics (off by default) are the `diagnostics.json` block of docs/04 §9 in the email body, shown in full in the sheet before Write email: app version, platform, language, schema version, the install's random sync node id, sync state with pending/conflict counts, and counts of tasks, Inbox, done, repeats, Trash and calendar events — never a title, note, email address or account id. A `mailto:` link can't attach a file, so the block is in the body (where the person can also delete it). The recipient is `FEEDBACK_EMAIL`; unset or the `.invalid` placeholder, the draft has no recipient. "What's new" = Settings › About › What's new, the changelog page (every release's notes, newest first, on the device); after an update that brought notes, a banner strip above every screen ("Dottoday 0.2.0 is here · See what's new · Not now") shows once — a strip, not a dialog, so it never stands between the person and their day; a fresh install shows nothing.

## Beyond v1 — standout roadmap and Phase 2

The milestones after v1's core (M7 calendars, M8 export/l10n/device QA) come from `11-standout-roadmap.md`:

| Milestone | Contents |
|---|---|
| M6.5 Delivery guarantees (before M7) | A0 alarms that fire, notification health, test alarm, background sync; B1 actual timestamps; B2 subtask durations |
| M9 See time | A1 Live Activity, ongoing notification, interactive widgets, controls, menu bar; B5 day snapshot; B6 App Intents |
| M10 Start | B4 ThinkingService (on-device first), B3 ProposalSheet, B1 Break it down, B2 Smallest step, B3 Unstick, A3 Focus |
| M11 Control | C1 Rebalance proposal, C3 Reality thread, C2 Routines, C4 energy suggestions (behind a switch) |
| M12 Reflect + capture | D1 weekly review + share, D2 low-energy mode, D3 thread journal, B6 capture anywhere, B4 brain-dump |

Phase 2 (ideas, not committed — the owner decides later): F1 Windows/Linux, F2 integrations (Reminders,
Google Tasks, Todoist, Notion), E1 body double, A2 wallpaper / watch face, the watch app (F3, ADR-0010),
B5 paper plan, shared/household threads.

Pricing principle: core free forever (R-18). The free/Pro split in `11-standout-roadmap.md` is a **draft
for the owner's review**; until it is signed off every feature is built ungated, and the only pricing
code is one `entitlements` service with a single `isPro` flag, true in all builds — no paywall, purchase
flow or store products.
